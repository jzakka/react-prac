# React学習記録：学習タスク管理アプリ

Next.jsとTypeScriptを使い、自分でコードを書いてブラウザーで確認しながらReactを学んだ記録。アプリは `task-app` にある。

バックエンド開発の基礎知識を前提に、環境を準備してチャプター2〜8に取り組んだ。記録日：2026年10月1日。

## 作った機能

- タスクの追加、完了状態の切り替え、削除。
- 「すべて・未完了・完了」の絞り込み。
- 全件数、未完了件数、完了件数、表示件数の表示。
- 空白だけの入力の拒否と、追加後の入力欄のクリア。
- Enterキーでのフォーム送信。
- localStorageへの自動保存と、再読み込み時の復元。
- 保存値がない場合、壊れたJSON、タスクの形式でないデータへの対応。

## 画面の部品とデータの流れ

**コンポーネント**は画面の部品。親の `Home` がタスクを管理し、子の `TaskItem` が1件の表示と操作を担当する。

**JSX**は、JavaScript内で画面の構造を記述する記法。波括弧でJavaScriptの式を表示に埋め込める。複数の要素を返すときは、親要素などでまとめる。

**props**は親から子へ渡す入力。文字列や真偽値だけでなく、関数も渡せる。子はpropsを直接変更せず、親から受け取った関数を呼び、親にstateの更新を任せる。

タスクの配列を `map` で表示に変換する。`key` はReactが各項目を識別するための目印で、通常のpropsとして子には渡されない。タイトルが重複・変更しても識別できるよう、IDを使った。

Next.jsのApp Routerでは、`task-app/app/page.tsx` がトップページを担当する。`"use client"` は、stateやクリック処理を使うClient Componentの入口を指定する文字列の宣言。

## stateと再レンダー

**state**はReactが保持する状態。更新関数を呼ぶと、Reactは新しいstateでコンポーネントを再実行し、必要な画面の変更を反映する。この再実行を**再レンダー**と呼ぶ。再レンダーは画面全体のDOMを書き換えることと同義ではない。

再レンダーでは `useState` も再び呼ばれるが、初期値を採用するのは初回だけ。Reactが関数の外側でstateを保持するため、毎回初期状態へ戻るわけではない。

件数や絞り込み結果は、元のstateから求める**派生データ**。コンポーネントの再実行で計算し直されるため、別のstateやEffectに保存しなくても表示が更新される。

Hookは `useState` などのReactの機能。条件分岐、ループ、イベント処理の中ではなく、コンポーネントの最上位で呼ぶ。

## 学んだHookの役割

| Hook | 役割 | 今回の用途 |
|---|---|---|
| useState | レンダーをまたいで状態を保持し、更新を依頼する | タスク、入力文字、絞り込み条件、読み込み完了状態 |
| useEffect | 画面への反映後に外部の仕組みと同期する | localStorageの読み込みと保存 |
| useMemo | 依存値が同じなら計算結果を再利用する | 表示対象のタスク配列の計算 |
| useCallback | 依存値が同じなら関数の参照を再利用する | 完了切り替え・削除関数 |

再レンダー時に現在のstateを受け取るのは `useState` の役割。`useEffect` がstateを読み戻すわけではない。

`useEffect` はReactが関数を実行する。一方、`useCallback` は関数を返すだけで実行しない。今回の切り替え・削除関数を実行するきっかけはボタンのクリック。

## 配列の更新とフォーム

stateの配列やオブジェクトを直接変更せず、新しい値を作って更新した。追加には既存要素を展開した新しい配列、切り替えには `map`、削除には `filter` を使った。

**スプレッド構文**は、配列の要素などを展開する記法。追加時には既存タスクを新しい配列に並べ、最大IDの計算ではIDの配列を `Math.max` の個別の引数へ展開した。

更新前の値が必要な場合、state更新関数に「前の値から次の値を返す関数」を渡す。Reactから更新前の値を受け取れる。

**不変性**は元のデータを書き換えないこと。**冪等性**は同じ操作を繰り返しても結果が変わらないこと。「必ず完了にする」は冪等だが、「完了状態を反転する」は冪等ではない。

入力欄は `value` と `onChange` でstateにつないだ。イベントから入力文字列を取り出して更新する。フォーム送信では `preventDefault` でページ移動・再読み込みという標準動作を止め、Reactの追加処理を行う。ラベルと入力欄は `htmlFor` と `id` で結び付けた。

## localStorageとEffect

localStorageはブラウザーの保存領域で、値は文字列として保存する。`JSON.stringify` で配列を文字列に変換し、`JSON.parse` で戻す。保存名は `learning-tasks`。

保存値がなければ `getItem` は `null` を返す。壊れたJSONは `try` / `catch` で扱う。JSONとして読めてもタスクの配列とは限らないので、配列かどうかと各要素のプロパティの型を検証してからstateへ反映した。

読み込み前の初期タスクで保存内容を上書きしないよう、`isLoaded` で保存を制御した。`finally` で、読み込み成功・失敗・途中終了のいずれでも読み込みの試行終了を記録する。

**依存配列**はEffectの再実行を判断するための値の一覧。初回に実行され、その後は依存値を前回と比較する。

| 指定 | 基本の実行タイミング |
|---|---|
| 省略 | 画面への反映のたび |
| 空配列 | コンポーネントが画面に登場した後 |
| 値を指定 | 初回と、いずれかの依存値が変わった画面への反映後 |

開発時には確認のため追加実行されることがあり、空配列でも必ず一回だけとは限らない。再レンダーのたびにすべてのEffectが実行されるわけでもない。

**クリーンアップ**はEffectで開始した処理の解除。タイマーや購読には必要だが、その場で終わる今回のlocalStorageの読み書きには不要。

## 関数の参照と最適化

コンポーネント内の関数は再レンダーのたびに新しく作られる。`useCallback` は関数の生成自体をなくすのではなく、依存値が同じときに以前の関数を返す。

親で関数をアロー関数に包んで子へ渡すと、その包む関数は毎回新しくなる。今回は共通の関数とIDを子へ渡し、子のクリック処理がIDを指定して呼ぶ形へ変更した。

**React.memo**はpropsを比較し、同じなら子の再レンダーを省略できる仕組み。関数のpropsは処理内容ではなく参照で比較される。`useCallback` だけで子の再レンダーが止まるわけではない。

Consoleで次を観察した。

- memo適用前：入力のたびに各TaskItemのレンダーログが出る。
- 関数の参照を保ちmemoを適用した後：入力だけでは子のログが出ない。
- 完了切り替え時：completedが変わった1件のログが出る。

**クロージャー**は、関数が作られたときの外側の変数を参照する仕組み。依存値を誤って省くと古い値を使う問題が起こり得る。今回の更新関数は、外側のtasksを読む代わりに更新前の配列をReactから受け取った。

useMemoとuseCallbackを外しても、追加・切り替え・削除・絞り込みは成立することを確認した。最適化は正しさのための必須条件ではなく、この規模で常に必要とも限らない。

## 残った疑問と次の取り組み

チュートリアルはチャプター8まで実施した。Effectの実行タイミングとuseCallbackとの違いを復習した。

引き続き整理したいのは、保存Effectが読む `isLoaded` を依存配列に含める理由と、「タスク変更時だけ保存する」という仕様との関係。現在の実装では、読み込み完了時にも保存する。依存配列を処理の入力としてどう考えるかは、次の復習項目として残す。

ユーザーが選んだ改善テーマ：

- 操作が分かりやすい、直感的なデザインへ改善する。
- console.log以外でも性能を観測できるようにする。レンダー回数だけで非効率と判断せず、処理時間も測定する。

次回はこの2つのどちらから着手するか決める。
